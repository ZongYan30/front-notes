# 回退机制 fallback

![熔断发生在模型组内的 Deployment；整个模型组不可用时，回退到其他模型组](https://zongyan30.github.io/front-assets/agent/litellm-circuit-breaker-fallback.png)


当一个请求到来，一个组内的所有Deployment都挂掉了，那么如果此时配置了回退机制，那就会执行配置的回退组。
```
group --> 网关分发 --> Deployment1  挂掉
                  --> Deployment2  挂掉

                  --> 触发回退机制
```

复现步骤:
1. 将目前组内的所有Deployment的credentials都写成错误的api key。
2. 发送一个请求到该组，会发现服务直接挂掉。

## 回退机制最佳实践

**同一个模型组内**：

- 平台统一
- 模型统一
- 不同账号

**回退组：**

- 不同平台
- 不同模型

回退组往往会配置为不同平台的模型，确保能够保证自己公司的业务能够继续运行。这里回退组选择deepseek来支持。

步骤如下：
1. 新建credential deepseek,名字为:Deepseek-backup-key1
2. 新建Add Model，配置如下：
```json
{
    "provider": "deepseek",
    "model": "deepseekv4-flash",
    "Mode Mappings": "chat-basic-backup",
    "Mode": "chat/completion",
    "existing credentials": "Deepseek-backup-key1"
}
```
3. 进入Settings-->Router Settings --> Fallbacks，新建一个Fallback:
```json
{
    "Primary Model": "需要支持的模型组(chat-standard)",
    "Fallback Chain": "退回的模型组(chat-basic-backup)"
}
```

再次发送一条请求，会发现模型返回了(由deepseek支持的)。
在LitellM的Log中，可以看到这次请求先重试了组内的Deployment，然后才触发了回退机制。


**骚操作**
我们仍然可以针对回退组的失败再设置一次回退支持，永远确保我们的业务能够继续运行。
