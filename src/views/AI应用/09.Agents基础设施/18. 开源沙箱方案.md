# 开源沙箱方案

## 实现沙箱的技术方案

| 方案            | 原理                                       | 隔离性               | 逃逸风险                   | 适用场景                       |
| --------------- | ------------------------------------------ | -------------------- | -------------------------- | ------------------------------ |
| Process         | 通过操作系统的进程权限和资源限制约束程序   | 取决于你的配置       | 较高，进程漏洞可能影响宿主 | 本地开发、运行低风险代码       |
| Container       | 通过命名空间和控制组隔离进程与限制资源     | 中等，与宿主共享内核 | 中等，内核漏洞可能导致逃逸 | 应用部署、运行受控的第三方代码 |
| Virtual Machine | 通过虚拟化硬件运行独立的完整操作系统       | 高，拥有独立内核     | 较低，需要突破虚拟化边界   | 强隔离、多租户、运行不可信代码 |
| ==MicroVM==     | 通过精简设备模型运行轻量级虚拟机和独立内核 | 高，拥有独立内核     | 较低，需要突破虚拟化边界   | Serverless、AI Agent 代码执行  |

## 技术实现

**底层技术实现**

| 名称            | 对应方案        | 定位           | 描述                                        |
| --------------- | --------------- | -------------- | ------------------------------------------- |
| sandbox-exec    | Process         | 进程沙箱工具   | 使用 macOS 的系统策略限制进程可以访问的资源 |
| ==Docker==      | Container       | 容器运行平台   | 创建和管理基于操作系统内核隔离的容器        |
| KVM             | Virtual Machine | 虚拟化基础设施 | 利用 Linux 内核提供硬件虚拟化能力           |
| VMware          | Virtual Machine | 虚拟化平台     | 创建和管理运行完整操作系统的虚拟机          |
| ==Firecracker== | MicroVM         | 微虚拟机监控器 | 创建启动快速、设备模型精简的微虚拟机        |

**上层技术实现**

上层技术实现封装了底层隔离技术，通过统一的 SDK 和 API 为开发者提供更易用的沙箱能力。

| 名称                | 定位         | 底层支持的技术方案                  | 描述                                             |
| ------------------- | ------------ | ----------------------------------- | ------------------------------------------------ |
| E2B                 | 云沙箱平台   | MicroVM（Firecracker）              | 通过 SDK 和 API 为 AI Agent 提供托管沙箱         |
| ==OpenSandbox==     | 开源沙箱框架 | Container、Virtual Machine、MicroVM | 统一管理 Docker 或 Kubernetes 中的多种沙箱运行时 |
| CubeSandbox         | 开源沙箱平台 | MicroVM（KVM、RustVMM）             | 提供面向 AI Agent 的高性能微虚拟机沙箱           |
| LangSmith Sandboxes | 托管沙箱平台 | MicroVM（自托管环境需要 KVM）       | 通过 LangSmith SDK 创建和管理隔离的开发环境      |
| 云服务              | 托管沙箱平台 | MicroVM                             | 阿里云、腾讯云、AWS均支持，通常兼容E2B           |

2. 新增`openSandbox`配置文件：`opensandbox_config.toml`（工程根目录，只读挂载进容器）：

   ```toml
   [server]
   # Server 在容器内监听所有网络接口；宿主机仅通过 Compose 映射到 127.0.0.1。
   host = "0.0.0.0"
   # Server 的 HTTP API 端口，需与 Compose 的容器端口一致。
   port = 8090

   [proxy]
   # Server 与动态沙箱不在同一 Docker 网络时，通过宿主映射端口代理请求。
   resolve_internal = false

   [runtime]
   # 使用宿主 Docker daemon 创建和管理沙箱容器。
   type = "docker"
   # 创建沙箱时注入 execd，提供命令执行和文件操作能力。
   execd_image = "docker.io/opensandbox/execd:release-1.1.0"

   [docker]
   # 动态创建的沙箱容器连接到 Docker 默认 bridge 网络。
   network_mode = "bridge"
   # Server 访问沙箱映射端口时使用的宿主地址；适用于 Docker Desktop。
   host_ip = "host.docker.internal"
   # 动态沙箱可分配的宿主端口范围起点。
   port_range_min = 40000
   # 动态沙箱可分配的宿主端口范围终点。
   port_range_max = 60000
   # 从沙箱容器移除这些 Linux capabilities，缩小容器权限。
   drop_capabilities = ["AUDIT_WRITE", "MKNOD", "NET_ADMIN", "NET_RAW", "SYS_ADMIN", "SYS_MODULE", "SYS_PTRACE", "SYS_TIME", "SYS_TTY_CONFIG"]
   # 禁止沙箱内的进程通过提权机制获得新权限。
   no_new_privileges = true
   # 限制单个沙箱容器可创建的进程和线程总数。
   pids_limit = 4096

   [egress]
   # 创建请求启用网络策略时使用的出站流量代理镜像。
   image = "docker.io/opensandbox/egress:release-1.1.0"

   [store]
   # Server 管理的元数据使用 SQLite；沙箱持久化卷由创建请求单独指定。
   type = "sqlite"
   # SQLite 文件位于 Compose 挂载的 opensandbox_server_data 命名卷内。
   path = "/root/.opensandbox/opensandbox.db"

   [ingress]
   # 沙箱入口采用直接访问方式，不启用独立的入口网关。
   mode = "direct"
   ```
